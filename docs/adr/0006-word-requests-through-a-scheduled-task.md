# Claude works through Word Requests in a cloud scheduled task that Nando wakes

So that the Owner can add a word from Nando itself, without opening the Claude app, the Owner types the word in Japanese search and picks the Group they found it in, and Nando stores a Word Request. Nando then wakes Claude by calling the API trigger of a cloud scheduled task (Claude Code on the web) on the Owner's own Claude subscription. The run reads `skills/japanese/word-requests/SKILL.md` from this repo, which takes each pending Word Request, follows the `add-word` skill for it, and records the outcome through the Module's Tools, over the same Connector the Claude app uses (ADR 0004). Nando never calls a model itself. This keeps ADR 0004's reasons for rejecting the Anthropic API, and adds a second way into the Connector that the Owner starts from Nando.

## Considered Options

- **Nando runs the loop with the Anthropic API**: Nando sends `SKILL.md` as the system prompt and the Module's Tools as client tools, and runs each `tool_use` in-process. It is faster, and leaving the destructive Tools out of the request would enforce "no destructive Tools from Nando" in code. Rejected for now, because it bills per token. Max's monthly API credit would cover it, but Pro gets none. It also needs a background runner on Cloud Run, which stops giving a request CPU once it has answered. If the risk below ever materialises, the Word Requests, routes and web app stay as they are, and only the part that wakes Claude changes.
- **An hourly schedule that drains the queue**: rejected. Cloud scheduled tasks run at most once an hour, so a word could wait an hour, and a run that finds nothing still uses the Owner's usage.
- **A schedule on the Owner's desktop** (Claude Desktop scheduled tasks, `/loop`, or `claude -p` from the OS scheduler): rejected. Nothing can wake it from outside, so it would have to poll, which means many empty runs. It also works only while that computer is on and awake, and the Owner adds words from the iPhone, away from it.
- **Calling Claude with the Owner's subscription token from nando-server** (`claude setup-token`): rejected. Those tokens can't use claude.ai connectors, and Anthropic's terms point apps at API keys, not subscription credentials.

## Consequences

- The scheduled task has **no schedule**, only an API trigger, so an empty queue costs nothing. Nando calls `/fire` when a Word Request becomes pending, unless it called it in the last 2 minutes or some Word Request is still claimed. Each run re-lists the queue until it is empty, so a word added mid-run is taken by the same run, but it stops after 10 Word Requests so that one session's context stays short. Nando fires again whenever a run resolves a Word Request and others are still pending with no claim, so a burst of words is worked through by a few runs in a row, and quiet hours cost nothing. A run is a new Claude Code session every time, and the trigger allows 30 fires an hour.
- Listing Word Requests claims at most 3 of them at a time, atomically, for 15 minutes. A Word Request whose claim lapses goes back to pending, and after 3 claims with no outcome it becomes failed. Core's half-hourly tick (ADR 0001) also lets the Japanese Module call `/fire` again when Word Requests are stuck, for example after the Owner's usage limit ran out. Core gains a way for a Module to do work at each tick, the way it already asks Modules for Notifications.
- **"No destructive Tools from Nando" is enforced only by the run's instructions.** The run reaches Nando over the Owner's Connector, and every Connector gets every Tool (ADR 0004). Nando can't tell a scheduled run from the Owner's own chat, so it can't refuse those calls. We accept this: `add-word` already asks before deleting, merging or moving a Word, and every run leaves a transcript at claude.ai/code. When a run thinks a merge or a Group change is needed, it records it as a suggestion on the Word Request for the Owner to act on in Claude Code. If a run ever does something destructive, we move to the Anthropic API option above.
- A homograph, or a question about which reading gets the kanji spelling, parks the Word Request with a question and choices. The Owner answers in the web app, and the Word Request goes back to pending with the answer attached.
- The Owner gets a Notification only when a Word Request needs an answer or has failed, at the next tick. Words added or improved show in the Pending strip of Japanese search, not as a Notification.
- Words still change only through Tools. Word Requests are the Owner's own asks, so the web app creates, answers, retries and dismisses them over `/api/japanese/`: the Japanese REST API's first write routes. A done or failed Word Request leaves the Pending strip when the Owner dismisses it, or 7 days after it finished. A retried Word Request gets 3 fresh claims.
- The trigger's bearer token is a secret like the VAPID key: it lives in Secret Manager and reaches Cloud Run through `deploy.yml`. Creating the scheduled task, attaching this repo to it and turning on its API trigger are manual steps in claude.ai. They can't be done from code.
- Cloud scheduled tasks are a research preview, and their API may change. How much of the Owner's usage one Word Request takes isn't documented, so we measure it on the first words.
