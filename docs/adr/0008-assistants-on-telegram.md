# Assistants talk to the Owner on Telegram, woken through a cloud scheduled task

The Owner wants to stop editing Nando in the web app, and wants a single place for their personal life, separate from the Claude app, which they use for technical and research chats. So Nando gets a Messenger: Telegram, with one bot for each Assistant. That means the Core Assistant, and one Assistant per Module (Career and Japanese first, Calories once it has Tools). Nando receives each message through the bot's webhook, stores it in that Assistant's Talk, and wakes Claude through the API trigger of one cloud scheduled task on the Owner's own Claude subscription, as for Word Requests (ADR 0006). The run claims one Assistant's waiting Talk and reads it. It answers through a Core Tool that sends the reply in the Messenger, and it reaches Nando over the Owner's one Connector (ADR 0004), and the Outside Services (Google Calendar first) over the scheduled task's own connectors. Nando still never calls a model itself.

## Considered Options

- **LINE**, the app the Owner already uses every day: rejected. Waking a run takes longer than a reply token lasts, so every answer would be a push message, and the free plan allows about 200 a month, around 6 a day. A paid plan costs several thousand yen a month for one person's chores.
- **WhatsApp or Instagram**: rejected. Both need a Meta business setup, and a business can message only within 24 hours of the Owner's last message, so a slow reply or a later follow-up could be refused or charged.
- **Telegram**: chosen. Bots are free, can send at any time, can have their own name and picture, and can download photos. The Owner uses Telegram for nothing else, so it is a space for Nando alone.
- **One bot for everything**: rejected. One chat per Assistant keeps each Talk on one subject, as the Owner's Claude app chats are not.
- **One long-lived cloud session per Assistant**, keeping the Talk in Claude's own memory: rejected. Nando can't bind or rebind a trigger from code (ADR 0006: setting one up is manual), and it couldn't tell when Claude's context is full. Nando keeps the Talk, and every run is a new session that reads it.
- **The Anthropic API, for replies in seconds**: rejected for the same reasons as in ADR 0004 and ADR 0006. A reply that takes a minute or two is acceptable for a chat.
- **One Connector, and one scheduled task, per Assistant**, so that Nando could refuse a Tool outside an Assistant's Module: rejected. Each would be set up by hand in claude.ai, and a slip only mixes up a Talk.

## Consequences

- Messenger and Talks belong to Core, like Connectors and Notifications. Core knows which Assistants exist, but nothing about what a Module's Assistant does.
- Only the Owner is heard. Nando knows the Owner's Telegram user ID from its configuration, and it drops every other sender's message without waking anything. Telegram user IDs are the same across bots, so one ID covers every bot.
- **An Assistant stays in its lane only because its instructions say so.** It may read anything in Nando and in the Outside Services, but it changes only its own Module, Core and the Outside Services, and it points the Owner to another Assistant for anything else. Every Connector gets every Tool (ADR 0004), so Nando can't refuse a write outside the lane, the same trade-off ADR 0006 made for destructive Tools. Each Assistant's skill lists the other Assistants, so that it can say which one to ask.
- Each Assistant has at most one run at a time. Messages the Owner sends while that run works, or before it starts, queue up in the Talk, and the run reads them before it stops. Wake rules follow ADR 0006: no second fire while a run for that Assistant is in flight or working, a fire that fails or never starts doesn't count after 10 minutes, and Core's tick fires again while messages are waiting. Two Assistants can run at the same time. The trigger allows 30 fires an hour for all of them together.
- When a message arrives, the bot reacts to it with 👀, and removes the reaction once a reply has answered it, so the Owner can see what is still waiting. Telegram's typing status also shows when a message arrives, and again each time the run calls a Tool. It lasts only 5 seconds each time, and Cloud Run gives Nando no CPU between requests to keep re-sending it, so the 👀 is what stays while a run is still starting. If no run has claimed them after 10 minutes, the bot says that Claude didn't start, for example because the Owner's usage ran out, and that Nando will retry.
- A Talk goes on until the Owner asks for a new one in their own words, which starts it blank, or until the run decides it has grown too long. In that case the run writes a short summary that opens the next Talk, and the bot says so in one line.
- Writes to Nando and to the Outside Services happen at once, and the Assistant says what it did. Deleting, merging or moving anything is always asked first, and the Owner's answer reaches a later run through the Talk. Claude never sends anything to anyone but the Owner: Suggested Replies stay drafts. (Amended by ADR 0009: the Core Assistant sends mail, but only a draft the Owner saw, on their yes in a later message.)
- The Japanese Assistant adds Words in the Talk itself, following `add-word`, and asks there about a homograph. Word Requests stay the web app's way in.
- Photos are read too ([#127](https://github.com/feriosch/nando-server/issues/127)), with the caption as the message's text. Nando keeps only Telegram's `file_id`, never the file, and a run sees a photo through a Tool that downloads it from Telegram when needed, so old photos aren't sent with every claim. A photo Telegram has dropped is gone for the run too. Other files, voice notes and stickers are still answered with a fixed line.
- PDFs of up to 10 MB are read as well ([#135](https://github.com/feriosch/nando-server/issues/135)), and an image sent as a file is read like a photo.
  - A PDF's text is extracted when it has some, and a scan's pages are drawn as images, at most 10 pages a call.
  - Nando does this itself, with poppler's programs run as separate processes, so it depends on nothing a Connector client may or may not do with a PDF, and a PDF that crashes one can't crash the server.
  - It moved the server image from `distroless/static` to `debian:12-slim`, with `poppler-utils`, CA certificates and a non-root user. The binary is still static and carries its own time zones.
- Notifications are sent in Telegram ([#128](https://github.com/feriosch/nando-server/issues/128)). Each goes to the chat of the Assistant its area names (the Core Assistant's for an area without one), and joins that Talk so the Owner can answer it, without waking a run on its own. Web Push was then removed, from the web app (feriosch/nando-web#88) and the server ([#137](https://github.com/feriosch/nando-server/issues/137)): Telegram is the only channel, and with no bot configured nothing is sent.
- Talks are not shown in the web app. Nando keeps them only to give each run its memory.
- Each bot's name and picture are set by hand in @BotFather. The bots' tokens, the webhook secret and the trigger's token are secrets like the VAPID key: they live in Secret Manager and reach Cloud Run through `deploy.yml`. Creating the scheduled task, giving it the Nando and Google Calendar connectors and turning on its API trigger are manual steps in claude.ai.
